LtRAM design review — deck outline

Assumed slot: 45–60 min including questions → 33 slides. Cutting guide at the end.

Audience: the Enzian team. They built the platform. Do not explain ECI, the CRB-2S, or the shell. Explain what you attached to it, why, and how you know it works.

Spine of the talk: NOR flash can be a memory tier, not a device — here is the hardware path I built, the kernel that drives it, and the evidence for each claim.

Part 0 — Frame (3 slides)

1. Title

  • LtRAM: presenting octal-DDR NOR to Linux as a memory tier over ECI
  • Your name, date, "design review — implementation and verification"
  • One line: 64 MiB working set living on NOR, transparently, at 4.8× DRAM

2. The thesis, in one slide

  • Claim: read-mostly pages can live on NOR instead of DRAM, chosen by the kernel, invisible to the application
  • Why it could work: read-mostly means the write penalty is paid once; NOR reads are ~5× DRAM, not ~1000×
  • Why it is hard, in one fact: a store to the NOR read window is silently discarded — no fault, no error, no signal
  • Everything in the design follows from that one sentence — say it early, refer back to it all talk

3. What I want from this review

  • Say it up front so they listen for the right things
  • Hardware: the read-capture timing problem (slide 11) — I have a proposed fix, want a sanity check
  • Kernel: whether NUMA node + custom zone is the right abstraction, or whether I should have used something else
  • Methodology: whether my verification is actually sufficient
  • Be explicit that this is a review, not a demo

Part 1 — Hardware / FPGA (12 slides)

4. Where the NOR sits

  • Micron MT35XU02GCBA octal-DDR NOR, 256 MB, 65,536 sectors × 4096 B
  • Attached to the VU9P, reached from the CPU over ECI
  • One page == one sector == 4096 B — this coincidence is load-bearing for the whole kernel design
  • Diagram: CPU ↔ ECI ↔ FPGA shell ↔ NOR bus ↔ flash

5. The programming model I exposed: three windows

  • rd_win — cacheable, coherent reads. The only thing the CPU does directly
  • io_win — uncached, DMA descriptors + a status word
  • er_win — erase trigger
  • Writes never come from the CPU. A descriptor to io_win makes the FPGA DMA the source page out of DRAM
  • Design consequence: the write path is asynchronous and must be waited on, not assumed

6. Bring-up: getting the bus to answer at all (folders 34–96)

  • FMC test → PHY verify → NVCR programming → the NorMorph M1/M2/M3 sequence
  • DDR I/O, IDDRE1 capture, SCK on an ODDR
  • SCK phase sweep 90/180/270°, then a 2-D sweep of SCK phase × read latency
  • Frequency ladder 20 → 200 MHz
  • Endpoint: 96_Mgr200 — proven controller + HLS managers + scheduler at 200 MHz. Base of everything after
  • One honest note: an IDELAY on the output SCK made the bus lie and was abandoned

7. Attaching ECI, and the write-path root cause (124_*)

  • Two accepted milestones before the real fix (v3 post-write, v4 realignment)
  • 124_8: a pure seed race with identical RTL — exhausted at floor −0.099. The lite-crossbar cone simply cannot be closed by seed spray. Knowing when to stop racing is a result
  • 124_10 — the root cause: axi_interleaver beat drop. GOLDEN v5. Clean 0/2048 checker, 0/4096-line census
  • 124_11: PSHA read responses, fixed civac → honest 13-hour-stable reads
  • Worth stating: clk_main is 150 MHz, not 200 — every comment saying otherwise is stale and has misled more than once

8. Two faults that look identical from a distance

  • The single most useful thing I learned. Both present as "bad words in a census"
  • Mode A — write side: sparse b16 program failures. Always bit 16, always 0→1, byte lane 2, sectors 16384–20479, ~7 ppm
  • Mode B — read side: gross 1→0 corruption, every bit, every region
  • They have different causes, different knobs, and different metrics see them
  • Set this up as the frame for the next three slides

9. Mode A: trail is a window, not a floor

  • trail = (earliest SCK pad arrival) − (latest DQ pad arrival), from report_datasheet on a routed checkpoint. Static, non-perturbing, no build required

  • It is an output quantity — both SCK and DQ are forwarded, so it says nothing about read capture

  • The table that makes the point — three bitstreams from ONE race of 179, identical RTL/frequency/seed, differing only in placement:

    trial trail census
    t57 +0.209 52 bad = 7 ppm, all b16, all 0→1
    t51 +0.433 0 bad (twice, independent)
    t44 +0.650 464,134 bad = 66,188 ppm, all bits, 1→0

  • Too little → sparse b16. Too much → the clk_out1/clk_out2 skew that buys pad-eye margin has eaten the internal margin feeding the DQ ODDRs

  • Target +0.433. All three bitstreams archived so the bracket can be re-run

10. Mode B: the read capture path has never been timed

  • Be blunt. This is the open hardware problem and this room can help
  • nor_controller.v captures reads with the flash's own strobe: IBUF → BUFG → IDDRE1(.C(rwds_clk))
  • RWDS is edge-coincident with returning DQ (Xccela/HyperBus convention — edge-aligned, not centered)
  • Used directly as the capture clock, it therefore samples DQ at its transition
  • The only thing centering the sample is incidental IBUF + BUFG + route delay: unconstrained, placement-dependent, a fixed number of ns
  • There is no input constraint anywhere in the design. nor_bus_eye.xdc has only set_output_delay; RWDS has only CLOCK_DEDICATED_ROUTE FALSE
  • That single fact predicts everything observed: a cliff at 198→199 MHz rather than a gradient, failure as the UI shrinks with frequency, and one DDR edge 15× worse than the other
  • Proposed fix: IDELAYE3 on RWDS is the textbook centering. A PLL phase shift is not available — RWDS is idle between reads, so a PLL cannot hold lock

11. The rule this produced

  • Never pick a build on trail alone
  • Trail bounds mode A and is blind to mode B by construction
  • The counterexamples that killed "trail predicts pass/fail":
    • 15199_f199 sits at +0.433 — same as golden — and produced 1.19 M bad words
    • 15178_f178 and 15189_f189 sit at +0.209 — the failing band — and both passed
  • Generalisable lesson: a static metric that bounds one failure mode will be mistaken for a predictor of all of them

12. Making the FPGA observable from the driver

  • io_win status word extension — free-running counters in the spare [63:24] bits, read as driver deltas: bytes, beats, pages, erases, hw_busy, er_infl
  • Why it matters: the driver can wait on the erase counter rather than a fixed sleep — a dropped trigger is invisible to a sleep and had bitten this project before
  • 142: read line reversal, found and fixed. read_manager ignored the ECI fillo (sub-line fill order) while echoing it, so concurrent reads got 128 B lines with their four 32 B chunks reversed. Fixed by pos ^ fillo; proven by VIO and 0 bad words at 222 MB/s
  • 140_n*: the ANTI_STARVE_N sweep — verdict INERT, N=2 and N=128 identical to five digits. Negative results are results

13. How I know 169_phy200 is good

  • Head-to-head against 179/t51 in the region where t51 fails. Identical harness, seed, parameters, trail. Only the bitstream differed → t51: 11 bad. 169: 0/0/0
  • 1.85 M-operation whole-device soak: 436 k writes, 1.48 M reads, read-bad = 0 — stopped voluntarily, not by a failure
  • Whole-device test=33: all 65,536 sectors, 125,465 writes, 240,071 reads, fill 0 / soak 0 / final sweep 0
  • test=42 census: 7,012,352 words, 0 bad, 0 ppm — per-bit none, per-region none
  • st_wait is the bitstream fingerprint: ~736–743 µs = 169_phy200, ~1329 µs = 179/t51. A hardware result is meaningless without knowing which bitstream produced it

14. What is still open on the hardware

  • The DQ→IDDRE1 capture path is unconstrained (slide 10)
  • Residual on 169: single bit, DQ5 or DQ6, always word 0 of a 128 B line (first beat after the address-to-data turnaround), always 1→0, flash content provably correct, ~1 in 48,000 reads
  • Two builds at the identical trail behave completely differently on it → a second build-dependent read-path factor exists and is unidentified
  • Per-pin output skew was measured and does not single out DQ5/DQ6 — useless as a build criterion
  • Say plainly: this is a live defect I have characterised but not explained

Part 2 — Linux / kernel (13 slides)

15. The hinge slide: what the kernel now has to believe

  • Transition from FPGA to kernel. Restate the one hardware fact
  • The kernel must guarantee: a flash-backed page is never writable, and never reaches the buddy allocator
  • Everything in part 2 is either enforcing that or measuring it

16. Design choice: NUMA node 1 + ZONE_LTRAM

  • The decision I most want reviewed
  • Alternatives considered: a block device (wrong — it's byte-addressable and coherent); DAX/pmem (closer, but I want migration, not a filesystem); a plain NUMA node (no way to keep the allocator off it)
  • Chosen: real node + a dedicated zone excluded from every zonelist, so nothing lands there by accident
  • Property: managed 0, numactl --membind=1 refuses rather than quietly handing over flash pages
  • Cost: a private page allocator (bitmap), because these pages never belong to buddy

17. Seven steps, each one bootable

  • 0 vanilla control → 1 workload → 2 node+zone → 3 read self-test → 4 write backend → 5 migration hook → 6 policy → 7 measurement
  • Every step is a git tag + an archived Image + a config + a result file
  • Method point: CONFIG_LTRAM=n is byte-identical to vanilla apart from four initcall names. One config symbol separates the two kernels, not two trees — which is what makes an A/B mean anything

18. Step 2: three traps, all silent by nature

  • Boot allocations land on flash by default. NUMA_NO_NODE + memblock's top-down search + the window being highest-PFN → per-CPU areas, swiotlb, qspinlock hash, CPU-entry page tables all on NOR, every store discarded. Also the memmap and the node's own pg_data_t
  • A new zone overflows GFP_ZONE_TABLE. 2⁴×3 = 48 fits in 64 bits; 2⁵×3 = 96 does not. The compiler only says "shift count >= width" from inside a macro
  • IS_ENABLED() still compiles its branch — naming ZONE_LTRAM inside one fails to build with the option off
  • Good slide for this audience: these are all platform traps, not LtRAM traps

19. Steps 4–5: the write backend, and where the hook goes

  • mm/ltram.c knows nothing about the FPGA — one function pointer, ltram_flash_ops::write_page
  • Until something registers, ltram_write_page() returns -ENODEV. That is the safety property, not a gap
  • Hook placement is the design decision: the flash write happens before folio_migrate_mapping(), while the source is already unmapped by try_to_migrate() and its contents are stable
  • Why: a flash error returns with nothing published. After the mapping moves there is no way to fail safely
  • The write path waits on the FPGA erase counter, not a sleep (callback to slide 12)

20. Step 6: what "read-mostly" means mechanically

  • The policy never looks at VMA flags, madvise, or any application hint
  • It reads PTE state, write-protects, and waits to see whether a write traps
  • clean_passes_required = 3; promote_batch = 32 chosen against the wear budget (65,536 sectors × 100,000 erases over 5 years = 41.5 erases/s sustained)
  • A policy that promotes faster than it can be wrong is a device-killer — the batch cap matters more than the interval

21. The detection problem — arm64's dirty bit is a one-way latch

  • Best technical slide in part 2. Take your time here
  • The scanner originally asked pte_dirty(). On arm64 that is pte_sw_dirty || pte_hw_dirty, and pte_sw_dirty is bit 55
  • Bit 55 is set on first write and nothing in this subsystem ever clears it: pte_wrprotect() sets it, pte_modify() preserves it across mprotect, pte_mkclean() is the only clearer and is called nowhere
  • This CPU has no hardware DBM (ID_AA64MMFR1_EL1 HAFDBS = 0), and arm64 has no soft-dirty at all (x86 selects HAVE_ARCH_SOFT_DIRTY; arm64 does not)
  • Measured cost of asking the wrong question: 13,247,550 of 13,258,954 scans rejected, zero weight pages ever promoted
  • Fix: ask pte_write() — is it writable right now — a question whose answer can change, and which the scanner itself changes

22. The result that matters: transparent detection

  • Phase A with mprotect vs phase B with no application hint of any kind
  • rej_writable == rearmed == 50,179, against exactly 50,176 weight pages
  • Pass 1 rejects every writable page and arms it exactly once; the app never writes again; pass 2 onward reads them clean
  • Armed exactly once each, never twice — the kernel measured the property instead of being told it
  • Phase B reaches the same promotion rate as phase A → the hint bought nothing; it only skipped pass 1
  • Reproduced independently on a second, unrelated program

23. Three bugs, each hiding the next

  • Frame it as a methodology slide, not a confession
  • They could only be found in this order, and each fix enabled the next discovery
  • Table: leak → page-cache promotion → stale cache lines
  • The line to land: a fix that makes a system exercise a path it never exercised before is not a regression when the next thing breaks

24. Bug 1 — the flash page leak

  • release_pages() / free_unref_page_list() — the batch path process exit and munmap take — bypass the __folio_put_small() hook
  • Pages hit the backstop in free_pages_prepare(), were correctly kept out of buddy, and were then dropped. 16,502 lost in one evening
  • Fix: return them at free_pages_prepare() — the one funnel every free path passes through. Covers all of them by construction rather than by enumerating call sites
  • Lesson: hook the funnel, not the callers

25. Bug 2 — page-cache folios were being promoted

  • The scanner had no anonymity filter, and it preferred file-backed text — read-only text is the most read-mostly memory a process has, and sits at the low addresses the batch fills first
  • Migration then took __buffer_migrate_folio(); the block layer can DMA into buffer heads hanging off those folios
  • Appeared in the trace of an uncorrectable SError panic (eight L2C TADs: LFB entry timeout + global sync CCPI timeout)
  • Honest caveat for this audience: async SError is imprecise — the reported PCs are not fault sites. Three CPUs took it at unrelated PCs. The trace named a real bug; it did not prove it was the trigger
  • Fix: anonymous, non-KSM folios only

26. Bug 3 — stale cache lines after a flash write

  • rd_win is ioremap_cached; an FPGA-side erase/program does not invalidate CPU caches
  • The harness verifiers always knew this — inval_sector() existed for exactly this reason. The migration path never called it
  • migrate_pages() publishes the new mapping the instant write_page() returns, so the first read can be served from a line belonging to the sector's previous occupant
  • Caught by the workload's between-run digest changing at run 12 of 15
  • The one to be careful about: the earlier run passed 15/15 and was passing for the wrong reason — the leak meant no sector was ever reused

27. How I verify — the gates

  • The digest is the gate. The workload recomputes SHA-256 after every pass and aborts on the first mismatch. A faster run with a different digest is corruption, not a result
  • --protect-weights proves the read-only premise instead of assuming it (exit 42 on violation) — an experiment control, not a kernel hint
  • Physical provenance read independently from /proc/pid/pagemap against the LtRAM range
  • Counters per rejection reason — the commit that did nothing but count is what turned a hypothesis into a measurement and disproved it
  • Off-box kernel log streaming, because pstore has never worked on this machine
  • Every baseline: git tag + Image + resolved config + result file, one commit per step

Part 3 — Results and open questions (5 slides)

28. The measurement

  • Show the three-phase curve (the chart)
  • One cold pass per point; cache scrub between passes, outside the timer
  • Both runs produce an identical digest, so the curves describe the same computation

29. What it costs

  • DRAM 0.1075 s/pass (sd 0.09%) → migrating up to 2.971 s (27.6×) → resident on NOR 0.5139 s (sd 0.08%) = 4.78×
  • The spike is not what NOR costs — it is what moving costs, paid once per page ever
  • Migration is erase-bound: ~16.4 ms/sector, serialised in one scan thread → ~36 pages/s
  • Reproduced 4.87× by an independent method the day before
  • Honest note: the LLC scrub changes the DRAM baseline by zero — a 64 MiB sweep against a 16 MiB shared LLC already self-evicts

30. What is verified, and what is not

  • Two columns. Do not blur them
  • Verified: detection with no hints; pages physically resident; correct readback; writes fault back to DRAM correctly (7,517 pages, 0 lost, 0 corrupted); the free path
  • Not verified: behaviour above the 256 MB window; concurrent write racing an in-flight promotion; step 5's negative test; steady-state re-measure after the cache fix
  • Known and unexplained: folio_isolate_lru() refuses 3–20% of selections; the DQ5/DQ6 read residual

31. Where I want your input

  • Is NUMA node + custom zone the right abstraction, or should this have been DAX/pmem with a migration policy on top?
  • The RWDS capture constraint — does the IDELAYE3 approach hold up?
  • Is promote_batch the right wear control, or should it be closed-loop on measured erase count?
  • What would you want to see before trusting this with a real workload?
