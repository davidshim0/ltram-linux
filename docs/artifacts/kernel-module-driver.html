Kernel, Module, Driver

Why the placement policy lives in 502 lines inside the kernel image while the code that actually touches the flash lives in a 6,937-line loadable module — and why that module is still an FPGA test harness. Short version: both are the kernel. A module is not "outside" it.

A loadable module is kernel code

The word "module" suggests something outside the kernel, like a plugin or a library. It is not. A .ko runs in the same address space, at the same privilege level, with the same power to corrupt anything, as code compiled into the kernel image.

The only real difference is when it is linked

There is no boundary to cross at runtime. When mm/ltram.c calls the backend's write_page, that is an ordinary indirect call through a function pointer — the same cost as any other call in the kernel. Nothing is serialised, nothing is copied, no context switches.

So the answer to "shouldn't it all be in the kernel?"

It is. Every line discussed here is kernel code running at EL1. The question is only whether a given file is linked into vmlinuz at build time or loaded afterwards with insmod — which is a packaging and lifecycle decision, not an architectural one.

What "driver" means, concretely

A driver is the code that knows how one specific piece of hardware behaves. Not "storage in general" — this chip, behind this FPGA, on this interconnect. It is where facts that are true of nothing else in the world get written down.

The facts that make it a driver

Every one of these is required to write a single page, and every one is specific to this board:

Each of these was a bug before it was a fact

The cache invalidation is the clearest example: it was missing from the migration path, and the workload's digest changed at run 12 of 15. The erase-counter wait replaced a fixed msleep that could not tell a completed erase from a dropped trigger. This is accumulated hardware knowledge, and it is exactly the kind of thing that must be isolated behind an interface rather than sprinkled through the memory manager.

What the memory manager must NOT know

mm/ltram.c has to remain true for any flash, behind any interconnect, on any board. If it knew that an erase takes 16.4 ms, or which address bit means "erase", then changing the FPGA would mean patching the memory manager — and during the FPGA campaign the bitstream changed 169 times.

What nor_eci_fulltest.c actually is

It is the FPGA bring-up harness. It was not written to be a driver; it was written to find out how the hardware behaves, over a campaign of 169 bitstreams. The LtRAM backend was added to it, in about 90 lines, because it already knew everything.

What those 43 tests are for

  • test=32 — erase, write and verify a run of sectors. The basic health check
  • test=42 — a 7,012,352-word census: per-bit and per-region error accounting. This is what proved 169_phy200 good and 179/t51 bad
  • test=33 — whole-device soak, all 65,536 sectors. 125,465 writes, 240,071 reads, zero failures
  • test=37, test=44, … — latency census, scheduler probes, the frequency ladder, the trail bracket

Every hardware fact on page 2 came out of running these. They are the reason we can say the flash is sound rather than hoping it is.

How it becomes a backend instead

It returns before starting the test worker. With provide_ops=1 none of the 43 tests run, no test traffic competes for the bus, and the module exists purely to answer calls from mm/ltram.c. The other 6,800 lines are inert — loaded into memory, never executed.

And that is the awkward part

We ship 1.4 MB of test harness to obtain ~90 lines of driver. It works, it is safe, and the inert code costs only memory — but it is not what anyone would design on purpose. Page 6 is about whether to fix it.

The seam: one struct, three function pointers

Everything the kernel knows about the flash hardware passes through a single structure. That is the whole interface — and its narrowness is a deliberate safety property, not an accident of layering.

"Optional" means the pointer may be NULL

The kernel checks before calling and degrades sensibly. No erase_page → the erase worker still recycles sectors, which is safe because write_page erases inline before every program. No device_idle → assume idle, which is correct only when nothing else drives the device. So the current backend, which implements neither, keeps working untouched.

No backend at all is a feature

The safety property

Until something registers, every attempt to write flash fails cleanly with -ENODEV, the migration aborts, and the page stays in DRAM, intact. A kernel with no backend cannot corrupt anything. That is why most of our tests deliberately run with the module unloaded: it isolates the placement policy from the device entirely.

The module cannot vanish mid-write

A write sleeps for ~16.4 ms. Without the pin, an rmmod during that window would free the code being executed. The reference is taken before the lock is dropped, so there is no gap. Running rmmod mid-migration is the leading explanation for the one unexplained hard reset this project has had.

Why a module rather than built in

Mostly one reason: iteration speed during a hardware campaign. The rest follows from that.

The campaign made this decisive

The FPGA and the driver co-evolved across 169 bitstreams. Many needed a driver change: a new status-word field, a different descriptor layout, a changed erase timing. If the driver had been built in, every one of those would have cost a full kernel rebuild and a reboot — on a board where the reboot is the slowest and least reliable step.

The property we would lose

A built-in driver is always present, so there is no such thing as running the placement policy without a device attached. Half the tests in this project depend on exactly that: load no backend, and every flash write fails with -ENODEV while the policy, the allocator and the state machine run at full speed with nothing at risk. That separation is worth keeping even after the hardware settles.

The cost we do pay

  • A .ko is tied to one kernel. Every kernel rebuild needs the module rebuilt against it, or insmod refuses on vermagic
  • Boot ordering. The boot-time read self-test cannot use the backend, because nothing is loaded yet — which is why it only reads, through its own mapping
  • 1.4 MB of inert test code resident for ~90 lines of driver

Should it become a real driver?

Eventually yes. Not now, and the reason is not laziness — it is that the test harness is currently the only thing that can tell us the hardware is sound.

When to do it

When the bitstream stops changing. At that point the hardware facts are frozen, the harness has done its job, and a ~400-line driver with a clear interface becomes strictly better: smaller, reviewable, and plausibly upstreamable. Doing it earlier means maintaining the extraction against a moving target, for no benefit anyone can measure.

What would change, and what would not

Nothing in mm/. The seam on page 4 is exactly what makes the swap cheap: a new module registers the same struct ltram_flash_ops and the memory manager cannot tell the difference. That is the point of having built the interface narrow in the first place — the policy has never known which device is underneath it, and it still would not.
