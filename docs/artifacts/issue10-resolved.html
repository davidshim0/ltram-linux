The Policy Never Promotes the Pages It Exists For

The scanner asked “has this page ever been written?” — a question that, on this CPU, is permanently answered yes for any page that has ever been touched. It now asks “is it writable right now?”, and detects the weights with no application hint of any kind.

What the measurement said

The hypothesis, and where it was wrong

The original diagnosis blamed matmul --protect-weights: it mprotects the weight region PROT_READ, making pte_write() false, so the write-observation re-arm never runs, so the dirty bit set during the initial fill is never cleared.

That was flagged at the time as not confirmed, and the first action taken was to instrument should_promote() with a counter per rejection reason (a06b6973c) rather than to act on the guess. That instrumentation is what showed the hypothesis was directionally right but wrong about the cause.

The correction

--protect-weights was not the cause. The defect was unconditional. Removing the flag would not have helped, because ptep_set_wrprotect() — the re-arm itself — sets the software dirty bit rather than clearing it.

The proposed fix (“have the re-arm clear the dirty bit for read-only mappings”) would therefore have fixed only the mprotected case and left the transparent case just as broken — which is the case that actually matters.

The actual defect

The scanner read pte_dirty(pte). On arm64 that is an OR of two very different things:

expressionexpands tocan it return to false?
pte_hw_dirty(pte)pte_write() && !pte_rdonly()yes — write-protecting clears it
pte_sw_dirty(pte)bit 55, PTE_DIRTYno
pte_dirty(pte)sw || hwno — the OR is poisoned by bit 55

Bit 55 is set the first time a page is written, and nothing in this subsystem ever puts it back:

  • pte_wrprotect() — sets it when the PTE was hardware-dirty. The re-arm made the problem permanent instead of resetting it.
  • pte_modify(), which backs mprotect, explicitly preserves it.
  • pte_mkclean() is the only function that clears it, and it is called nowhere in LtRAM.
  • Hardware dirty-bit management would clear nothing either — this CPU does not have it (ID_AA64MMFR1_EL1 HAFDBS = 0).
  • arm64 has no soft-dirty at all: x86’s Kconfig carries select HAVE_ARCH_SOFT_DIRTY, arm64’s does not, and there is no PTE_SOFT_DIRTY to borrow.

What that adds up to

Under the old rule the policy could only ever promote a page that had never been written since its PTE was established. Any page written even once was permanently ineligible — for the lifetime of the process, with or without mprotect. Weights are written exactly once, at fill, which is enough to disqualify them forever.

The 8,384 pages the broken scanner did select were the process’s never-written pages — freshly faulted file and anonymous pages — not the weights.

The fix

commitwhat it does
a06b6973ccount why a scanned page was not selected — turned the hypothesis into a measurement, and disproved it
f558a316fa flash page may never be writable, and may never reach buddy — guards do_wp_page’s reuse path (forcing the copy, which is the demotion), remove_migration_pte’s pte_mkwrite, __folio_put_small’s free path, plus a free_pages_prepare backstop
244a66761ask whether a page was written, not whether it was ever written

f558a316f is what makes running without --protect-weights safe. A store to the flash read window is silently discarded by the hardware — no fault, no error — so a flash-backed page that is ever allowed to become writable loses data with no diagnostic. Until this commit, the only thing preventing that was the mprotect turning the write into a SIGSEGV.

The evidence

Two phases, same binary, same size, same 240 s attach window, counters sampled before and after and reported as deltas. --protect-weights is an experiment control, not a kernel hint — the policy reads PTE state and never looks at VMA flags.

It is the defect, measured directly.

Phase B — no --protect-weights, no hint at all

The line that proves it

rej_writable == rearmed == 50,179, against exactly 50,176 weight pages (205,520,896 B ÷ 4096, exact — the other three are heap and data). The whole mechanism is visible in that one equality:

  • Pass 1: all 50,176 weight pages are rw-p and writable → rejected, and every one write-protected.
  • The application never writes them again. It is read-mostly; the kernel simply did not know yet.
  • Pass 2 onward: pte_write() is false → they read clean → clean runs accumulate → selected.

Armed exactly once each, never twice — no weight page was ever re-dirtied. The kernel measured the read-mostly property instead of being told it.

Two ways to misread these counters

A large scanned is the symptom of finding nothing

ltram_scan_once() calls walk_page_range(mm, 0, TASK_SIZE, …) — it restarts at address 0 every pass with no cursor — and the PTE loop is gated on ctx->nr < promote_batch. Once 32 pages are selected the rest of the pass short-circuits and stops counting. Under the old rule nothing was ever selected, so every pass had to walk all 13.2 M pages to the end. 13.2 M → 110,732 is the fix working, not a regression.

110,732 ÷ 233 passes = 475 pages per pass. /proc/PID/maps confirms those are the weights and not incidental heap: the 196 MiB anonymous region is the lowest mapping in the mmap area, with only ~39 pages of binary and heap below it.

sel_isolated measures the batch cap, not the predicate

promote_batch = 32 at one pass per second caps promotion at 32 pages/s. Both phases saturated it on every pass (7,456 ≈ 32 × 233, and 7,488). The 50,176 weight pages would take 26 minutes to drain even with detection perfect. It is live-writable at /sys/module/ltram_policy/parameters/promote_batch, so it is a knob, not a rebuild — but the 32/s default is set by the wear budget (41.5 erases/s sustained), so raise it for measurement only.

What this run does not prove

  • Nothing reached flash. The nor_eci backend was deliberately not loaded, so all 7,456 / 7,488 isolated pages found no write path and were put back in DRAM intact. promoted 0 and promote_failed == sel_isolated are arithmetic, not symptoms. Held out for two reasons: the 08-19 comparison run also had no backend, and changing the predicate and the driver together would make the delta unattributable.
  • demoted 0, so the guard in f558a316f is still unexercised. It only fires once a page is actually on flash.
  • sel_isolate_fail is 1,627–2,081, ~18–22% of every selection — folio_isolate_lru() refusing. Not new and not caused by this fix, but it is a fifth of the promotion budget being dropped, and it was counted nowhere before a06b6973c.

The lesson worth keeping

The hypothesis was plausible, fit every number available, and was wrong about the cause. What separated it from the truth was one commit that did nothing but count. A counter per rejection reason cost less than an hour and would have answered this on the first run — its absence is why the diagnosis stayed a guess for a day.
