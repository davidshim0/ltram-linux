1.2 The address map, and why the base is not a round number

The base is three address bits, each meaning something. The high bits are decoded by the FPGA, so the address itself is part of the protocol.

bitvalueselects
400x10000000000node — routes to node 1 (the FPGA) rather than node 0 (DRAM)
380x04000000000marker — separates NOR traffic from DMA traffic, which share the coherent virtual channels
390x08000000000erase — set on top of the other two

0x10000000000 would reach the FPGA with the marker clear — nothing in the request would say which subsystem it is for. DRAM tops out at 0x1fffffffff (bits 0–36), so bits 38–40 are all above real memory and cannot collide.

Node 1 is exactly one zone

mm/mm_init.c:1282 gives every zone on node 1 except ZONE_LTRAM a span of zero; arch/arm64/mm/init.c:171 ends ZONE_NORMAL exactly where the window begins, so ZONE_LTRAM spans nothing on node 0. A bijection, enforced in two places that must agree. Verified: spanned/present 65536, managed 0, and numactl --membind=1 refuses.

1.3 Buddy never allocates a flash page — four independent reasons

mechanismblocks

not GFP-selectable (GFP_ZONES_SHIFT stays 2)no gfp_t can name it. There is no way to ask
free_pages_prepare() returns falseeven a page arriving by mistake is returned to our allocator, not freed into buddy

To be in buddy is to accept arbitrary use — a page table, a kernel stack, a DMA buffer. Any of those on NOR means stores silently discarded. So allocation is a private structure, described next.

1.4 · The four page states

The distinction that keeps the wear model honest

A page allocated as a migration destination whose migration then failed was never written, so its sector is still blank and goes straight back to FREE. Only a page that really held data goes to DIRTY. Wrong in one direction costs a 16.4 ms erase per failed migration for nothing; wrong in the other hands out a sector still holding the last tenant's data — and the workload's digest is what catches that.

How each state is represented, and why they differ

staterepresentationsizewhy
VALIDbitmap8 KiBNo ordering needed. bitmap_weight() derives the count, so a count cannot drift from what it counts. Disjointness is one bitwise AND
DIRTYbitmap8 KiB
ERASINGone u324 Bthe device erases one sector at a time; a queue would never hold more than one thing
FREE101 bucket lists by erase count, nothing else1 MiBfree is ~(VALID|DIRTY) minus erasing, so it is derived at check time and cannot drift. A stored bitmap would be a fourth structure able to be wrong in the same way as what it checks
erase countsu32 ec[65536]256 KiBmust survive while a page is VALID or DIRTY, so the bucket index cannot hold it

Buckets at 1000-erase granularity, FIFO within. Not a compromise: while every page shares an erase count they all sit in bucket 0, and pop-head / return-to-tail is round-robin. Exact per-count buckets behave identically there and cost 100,000 list heads instead of 101. RETIRED is deliberately absent — it only means something once the wear-parking policy exists, and carrying it now would mean a permanently empty bitmap.

Allocation: the least-worn page, and what it replaced

No cursor or hint: scanning 101 buckets is cheaper than the find_first_bit() it replaced (101 list_empty() loads against a 1,024-word bitmap scan), and a hint would be wrong anyway — erase counts only rise, but a page that sat VALID at a low count returns to a bucket below where a hint had drifted.

Measured: peak wear per sector, 1,518 → 1

Same workload, two kernels. find_first_bit always returned the lowest free index, so a released page was handed straight back out: one sector absorbed 1,518 allocations while 65,535 were never touched. With buckets, total_allocs == pages_ever_used == 2,752 — every allocation went to a different page, and no page was handed out twice.

The lock, and one thing to correct

There are not 48 instances of Linux

One kernel image runs across all 48 cores. They share one physical address space and one copy of every data structure — a single bitmap at a single address that all 48 load and store directly. The arbitration problem is real, but it is not consensus between instances; hardware cache coherence makes their views agree and the lock decides who may mutate now.

A spinlock is one word: test-and-set, and spin if held. Never sleeps — right when the critical section is nanoseconds, because sleeping and waking costs more than the wait. The contrast is in this same project: the backend's flash write uses a mutex, because holding for ~16.4 ms would burn 32 million cycles spinning.

irqsave prevents a one-core self-deadlock: the free path is reachable from softirq via free_pages_prepare(), so a core holding the lock in process context that then took an interrupt wanting the same lock would spin forever waiting for itself. It masks interrupts only on the local core; the other 47 are still handled by the lock.

1.5 · The background erase engine

Why this exists

costshare
subsector erase16.4 ms93%
programming a sector~1.2 ms7%

write_page() erases synchronously before every program, so 93% of a promotion's cost is erase, on the critical path. Pages arriving pre-erased cost the DMA alone. It removes the erase from the latency path, not the throughput budget — sustained promotion is still capped near 61 pages/s. Ours is a burst workload, so we collect the win.

A workqueue, not a timer

The erase sleeps ~16.4 ms inside the backend waiting on the device's erase counter (never a fixed delay — a dropped trigger is invisible to a sleep), and timer callbacks run in softirq where sleeping is forbidden. The worker drains erase_batch per invocation and re-arms with zero delay while a backlog remains: one erase per 50 ms poll would have capped the engine at 20/s against a device sustaining ~61/s.

The device-idle gate

Reads never reach the driver — they are plain loads through the cacheable window — so the FPGA's status word is the only way the kernel can see them at all. RDDATA is why it can. A single sample can land in the gap between two reads, so the device must look idle idle_samples (3) times in a row before a 16.4 ms erase is committed. Not quiet → back to DIRTY, erase_deferred++, never erase into a read stream.

Lazy erase is correct, and it invalidates an obvious assertion

The hysteresis was a comment, not code — found 26 Aug

The gate tested erase_high_water and nothing else. erase_low_water was declared, exposed as a module parameter and documented, but never read — so the code did precisely what its own comment said it was avoiding: at the mark, each allocation drops free below it, one sector is erased, free rises back, and the engine stops. One erase per allocation, with the erase_batch drain defeated every time.

It hid because free has never come near the mark — the largest run so far promoted 8,846 of 65,536 pages and left free at 56,690. Now latched: on below the low mark, off at the high one, holding state in between. The “off” test runs first, so a nonsensical low > high set through sysfs degrades to the old single threshold rather than latching on forever.

DIRTY does not drain, and should not

Erasing starts only below erase_low_water and continues to erase_high_water — hysteresis, so the engine is not started and stopped once per allocation at a boundary. After a workload exits, free sits far above the high mark, so the worker deliberately does nothing and DIRTY simply accumulates. Spending erases on sectors nobody needs is pure wear.

So “free returns to 65,536” is the wrong success criterion once a backend is loaded. The right one is the four states summing to 65,536. An earlier test asserted the former and would have failed on correct behaviour.

Making the gate visible

“Gated because free is above the high mark” and “the worker is wedged” produced identical output — both just erases_done 0 — and the first is the design working. That ambiguity is what hid the bug above, so pagestate now says which it is:

The current test cannot exercise the erase engine

At default watermarks the engine only opens below 2,048 free, so a test would have to promote ~57,000 of the 65,536 pages to reach it. The watermarks are module_param(…, 0644) on built-in code, so they are live at /sys/module/ltram_policy/parameters/ and can be raised to force the engine on against a pool of DIRTY pages that already exists — no reboot, no larger workload. That is a prerequisite for inline_erase=0 meaning anything: trusting a pre-erased pool requires the pool to have been erased.

1.6 · The invariant, and the four guards

The invariant

A flash-backed page is never writable, and never reaches the buddy allocator. A store to the NOR read window is silently discarded by the hardware — no fault, no error — so a writable flash PTE loses data with no diagnostic whatsoever.

sitefile:lineprevents
write faultmm/memory.c:3516do_wp_page reusing a flash folio in place. Falls through to wp_page_copy() — which is the demotion
migration entrymm/migrate.c:230remove_migration_pte restoring a writable PTE — the one route to a writable LtRAM PTE not passing through do_wp_page
single-page freemm/swap.c:113__folio_put_small handing a flash page to buddy
every other freemm/page_alloc.c:1102the catch-all. free_pages_prepare() is the one funnel every free path passes through

Why the fourth site is the one that matters

release_pages() and free_unref_page_list() — the batch path that process exit and munmap take — bypass __folio_put_small() entirely. With only the first three, flash pages hit the backstop, were correctly kept out of buddy, and were then dropped: 16,502 leaked in one evening.

Measured since: in one run 4,452 frees took the batch path and 3 took the single-page path. At process exit the batch path is not one of two routes, it is effectively the only one.

The predicate is one line

Why pte_write(), and why there is no streak counter

The original predicate asked pte_dirty(). On arm64 that is pte_sw_dirty || pte_hw_dirty, and pte_sw_dirty is bit 55, a one-way latch: set on first write, set again by pte_wrprotect(), preserved by pte_modify(), and cleared only by pte_mkclean() — called nowhere here. No hardware DBM (HAFDBS = 0), no soft-dirty on arm64. Measured cost: 13,247,550 of 13,258,954 scans rejected, zero target pages ever promoted.

A page also used to need N consecutive clean sightings, which meant a counter per pfn in an xarray that was never erased — an unbounded leak, plus an xa_load on every PTE of every pass. It bought nothing: how much confidence “not writable when we looked” carries is set by how long the page had been write-protected, and scan_interval_ms × scan_ptes_per_pass already control that. One knob, no metadata.

The minimum is still two sightings — one to arm, one to confirm. That is not extra waiting; a page cannot be known read-only until it has been protected and left alone. A page already non-writable when first seen is promoted on the first sighting.

The scan resumes; it does not restart

The walk used to restart at address 0 every pass and stop once the batch filled, so anything above that point was never examined — a second large region above the first would have starved indefinitely, and the only reason none did is that mmap happened to place the region we cared about lowest. It also re-examined the same low PTEs every second, which is why ptes_examined reached 13.2 M over an address space of 50,176 pages.

Measured: the cursor works

sweeps 1, scan_cursor 0xf89666fbe000, and ptes_examined / chosen at 3.8× where it was 1:1 before. It is now walking past regions instead of re-hitting the same eligible pages.

Consequence worth knowing: a page is sighted once per sweep, so the sweep time is the observation window.

2 · Method

2.1 The measurement boundary

Inside the timer

  • the ITERS × N × N inner loop, and nothing else
  • every read of W, which is what crosses to NOR once promoted

Outside the timer

  • memset(y) and cache_scrub()
  • the SHA-256 digest and its comparison
  • every printf, including the POINT line
  • the entire --phys pagemap census

now() is CLOCK_MONOTONIC, and the clock stops before the digest, so verification never inflates a timing.

2.2 The cache scrub — and it changes nothing

  • Capacity eviction, not dc civac — needs no privilege and does not depend on which cache-maintenance instructions EL0 may issue
  • 64 MiB against a 16 MiB LLC. This machine has no private L2: 16 MiB is the LLC, shared by all 48 cores
  • The store pass exists so the scrub buffer cannot itself be promoted. Without it the buffer is anonymous and read-mostly — a perfect candidate — and mmap places it below the weights, so the scanner promoted all 16,384 pages of the instrument before touching the subject, burning 457 s and 16,384 erases

Measured: the flush is a no-op at this size

DRAM baseline warm 0.1074 s, cold 0.1074 s, identical to four decimals over six runs each. A 64 MiB linear sweep against a 16 MiB cache self-evicts before it wraps, so these timings were always effectively cold. The flag is kept because it forecloses the objection, not because it changed an answer. If you need a warm-cache number, this method will not give you one.

2.3 What one point is, and how residency is measured

  • --iters 1 --runs N → one point = one cold pass over the whole region. With --iters K, iterations 2..K are warm
  • Residency comes from /proc/pid/pagemap compared against /sys/kernel/debug/ltram/{start,end}_pfn — page-table truth, not the policy's opinion, so it would catch a counter that lies
  • Root is required. Unprivileged pagemap on this box reports every page absent; the tool warns rather than reporting a silent zero
  • Alignment: matmul prints TSTART as a CLOCK_REALTIME epoch at the run loop's origin, so a sampler needs no guess about how long the fill took

The rule

A faster run with a different digest is corruption, not a result. On this hardware corruption is silent by default, which is why the digest gate is not a formality — it caught the stale-cache-line bug at run 12 of 15.

3 · The test

One script, ltram-test.sh, replacing five. --flash toggles the backend rather than having separate files.

There is no --protect-weights in it, and there never will be

It mprotects the region PROT_READ, so pages arrive already write-protected and are promoted on first sighting — which means the arm → wait → promote cycle, the entire detection mechanism, never runs. It hid that from three separate runs before it was noticed. The policy reads PTE state and has never looked at VMA flags, so the hint proves nothing it does not also conceal.

Without --flash, no backend is loaded: every flash write fails -ENODEV, so no sector is ever programmed and nothing can reach DIRTY. The policy, allocator and state machine run at full speed with nothing at risk. That separation is why most testing is done that way.

5 · What would falsify these

Stated so you can check them rather than take my word

  • Both 4.78× measurements predate 1c. They agree with each other, which is reassuring, but neither came from a kernel with the current state machine. A steady-state re-measure is outstanding
  • The on/off delta mixes three things — flash read latency, NUMA distance, and migration cost. Separating them needs a DRAM-backed node-1 control that does not exist. Until it does, the delta is a combined figure
  • One access pattern. A 64 MiB sequential sweep. Random access, or a set that fits in LLC, would land elsewhere. 4.78× is not a constant
  • Above the 256 MB window is untested. Every result here depends on each page getting its own sector, written once
  • A write racing an in-flight promotion is untested — the writeback test deliberately avoids that race rather than exercising it
  • Path A is under-tested. Demotions take __folio_put_small(), and our workloads exit rather than churn, so 4,452 frees took the batch path against 3 single-page. A write-heavy workload would invert that
  • Step 5's negative test has never run. Without it, hook placement is argued from code reading — the positive path passes whether or not the hook precedes folio_migrate_mapping()
  • erases_done is still 0 — correctly, the engine has never been ungated. The worker, the watermarks and the idle gate are compiled and, as of this writing, unexercised against a real erase. Every claim about erase throughput here is arithmetic on the device's 16.4 ms figure, not a measurement of this code path

A methodology note that cost four hypotheses

Ten pages stayed VALID after a workload exited, and were called a leak. In order, the explanations offered were: a refcount 2→1 across a COW (ordinary — LRU membership holds one); waiting for reclaim (they were not on an LRU to reclaim from); destinations stranded on a migration failure path (dst_released 0 — there were no failures); and a genuine reference leak (they released themselves).

They were folios sitting in per-CPU folio batches, draining lazily. The measurement that settled it was reading the same file twice and noticing a counter had moved. Every wrong answer came from reasoning about counters instead of looking.
