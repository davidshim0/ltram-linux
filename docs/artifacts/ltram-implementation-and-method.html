1.3 The memory model

  • LTRAM_PHYS_BASE = 0x14000000000, LTRAM_PHYS_SIZE = 256 MiB, LTRAM_NUMA_NODE = 1 — all in include/linux/ltram.h:35-37
  • Node 1 is a real NUMA node with a dedicated zone, ZONE_LTRAM, excluded from every zonelist
  • Consequence, verified on hardware: spanned/present 65536 but managed 0, and numactl --membind=1 refuses with an allocation failure rather than quietly handing over flash pages
  • These pages never belong to buddy. Allocation is a private bitmap in mm/ltram_policy.c (find_first_bit, so sectors are handed out ascending and contiguous), under a spinlock taken irqsave
  • Boot allocations, the memmap (sparse.c) and the node's own pg_data_t (arch_numa.c) are all forced to node 0

1.3.1 Why the base is 0x14000000000 and not 0x10000000000

The base is not a number someone picked — it is three address bits, and each one means something. On this platform the high bits of the physical address are decoded by the FPGA, so the address itself is part of the protocol.

bitvaluewhat it selects
400x10000000000the node bit — routes the request to node 1 (the FPGA) instead of node 0 (DRAM)
380x04000000000the marker bit — separates NOR traffic from DMA traffic, which share the same coherent virtual channels
390x08000000000the erase trigger — set on top of the other two to make an access an erase rather than a read

So 0x10000000000 would be node 1 with the marker bit clear. The request would reach the FPGA, but nothing in it would say which subsystem it is for — NOR reads and DMA traffic ride the same coherent VCs, and bit 38 is what tells them apart. The read window is therefore node | marker = 0x10000000000 | 0x04000000000 = 0x14000000000, and the erase window is the same thing with bit 39 added.

Why these bits are free to use

DRAM on this machine tops out at 0x1fffffffff — 128 GiB, which occupies bits 0–36. Bits 38, 39 and 40 are all above the top of DRAM, so none of them can collide with a real memory address. The window sits at 1.25 TiB in a 128 GiB machine precisely because that region is otherwise unreachable.

Source: include/linux/ltram.h:32-35 and ltram-backend/nor_eci_fulltest.c:35-37. The kernel and the driver define the same constant independently and must agree — ft_ltram_write_page() range-checks every pfn against its own copy and returns -EINVAL if they ever drift.

1.3.2 Node 1 is exactly one zone — and that zone exists nowhere else

Short answer: node 1 ≡ ZONE_LTRAM. It is a bijection, enforced in two places that have to agree.

Direction 1 — node 1 has no other zone

Every zone on node 1 other than ZONE_LTRAM is given a span of zero. There is no ZONE_DMA, no ZONE_NORMAL, no ZONE_MOVABLE on node 1 — they exist as enum entries but describe nothing. And absent = 0 because the flash is physically contiguous, so the zone has no holes.

Direction 2 — ZONE_LTRAM is empty on node 0

free_area_init() derives each zone from the previous zone's boundary, so ZONE_NORMAL is made to end exactly at ltram_start_pfn. Node 0's pfns all fall below that boundary, so ZONE_LTRAM spans nothing there. ZONE_DEVICE sits between the two with its max_zone_pfns[] entry left at 0, which free_area_init() renders as empty without disturbing the boundaries.

The bug this comment records, because it is easy to reintroduce

Setting both entries to max_pfn — which this code used to do, while its comment claimed otherwise — makes ZONE_LTRAM span max_pfn..max_pfn, i.e. nothing, and lets ZONE_NORMAL swallow the window:

Normal   [mem 0x0000000100000000-0x000001400fffffff]
LtRAM    empty

That is the failure mode to check for on any boot: if ZONE_NORMAL's range extends past 0x14000000000, the allocator believes flash is ordinary memory.

What that buys, and how it was verified

  • ZONE_LTRAM is absent from every zonelist (build_zonerefs_node), so no allocation can ever reach it. Pages arrive only by migration
  • It is not GFP-selectable. include/linux/gfp.h:92-105 keeps GFP_ZONES_SHIFT at 2, exactly as ZONE_DEVICE does — counting either zone overflows GFP_ZONE_TABLE (24×3 = 48 fits in 64; 25×3 = 96 does not), and the compiler reports that only as a shift-count warning from inside a macro
  • Verified on hardware: Node 1, zone LtRAM with spanned/present 65536 and managed 0; stray_allocs 0; and numactl --membind=1 refuses with a page allocation failure rather than quietly handing over flash pages

managed 0 is the load-bearing observation: the buddy allocator has been given none of these 65,536 pages, which is why a private bitmap allocator exists at all.

1.3.3 The buddy allocator never sees these pages — and cannot

Correct: buddy never allocates a flash page. Not "is discouraged from" — four independent mechanisms each make it impossible, and any one of them alone would suffice.

#mechanismwherewhat it blocks
1managed_pages = 0mm/mm_init.cbuddy was never given the pages. Its free lists start empty and nothing ever adds to them
2absent from every zonelistbuild_zonerefs_nodethe allocator's search never visits the zone, on any node, for any request
3not GFP-selectableinclude/linux/gfp.h:92-105no gfp_t mask can name ZONE_LTRAM. There is no way to ask
4free_pages_prepare() refusesmm/page_alloc.c:1102even a page arriving by mistake is returned to the bitmap and not freed into buddy

Mechanism 4 is the backstop for the other three: if 1–3 were ever defeated, a flash page still could not enter buddy's free lists, because the one funnel every free path passes through turns it away.

How a page is allocated, both ways

Note the last step. A buddy page arrives with its refcount and page flags already established. A flash page does not exist as far as the core allocator is concerned, so ltram_alloc_page() has to do that by hand — set_page_count(p, 1) and clearing PAGE_FLAGS_CHECK_AT_PREP — "the way the migration core expects".

How a page comes back — and why there are two routes

This diagram is the shape of a real bug we shipped

The original guard hooked only __folio_put_small() — the left branch. The right branch is the one process exit and munmap actually take, and it bypasses that hook entirely. Flash pages hit free_pages_prepare(), were correctly kept out of buddy, and were then dropped: 16,502 pages leaked in one evening, a quarter of the window.

Measured proof of which branch dominates: in the station-4 run late_free (the funnel) counted 6,779 against 7 for a run dominated by demotion (the single-page path). They are genuinely different routes and both must be covered.

Why it had to be a private allocator

  • To be in buddy is to accept arbitrary use. A page on a buddy free list can be handed to a page table, a kernel stack, a DMA buffer, a slab. Any of those on NOR means stores silently discarded — and on this hardware that is not a fault, it is data loss with no diagnostic
  • managed_pages feeds watermarks, OOM and /proc/meminfo. Counting 256 MiB of flash as free memory would make the kernel believe it has memory it can never hand to anyone
  • There is no gfp bit left to select it with. GFP_ZONE_TABLE overflows at a fifth GFP-selectable zone, so even if we wanted buddy to allocate flash on purpose, there is no way to express the request

Two consequences worth checking rather than assuming

  • Promoted pages go back onto an LRU (migrate_pages does this, and the scanner calls putback_movable_pages()). So reclaim can in principle select a flash-resident page and try to swap it — reading from NOR to write to swap. Whether that is correct, merely wasteful, or a problem has not been tested
  • The bitmap has no erase-count memory. It cannot, because it is rebuilt at boot. Wear levelling would need persistent per-sector counters, which do not exist yet

The alternative that deserves review

ZONE_DEVICE with devm_memremap_pages() is the upstream mechanism for exactly this shape of problem: pages that are real, refcounted and mappable, but not owned by buddy. DEVICE_COHERENT in particular describes coherent, CPU-accessible device memory — which is what this NOR window is.

We did not use it, and the honest reason is that a dedicated zone was the shorter path to a bootable kernel, not that ZONE_DEVICE was evaluated and rejected. It would have supplied the page lifecycle we had to write by hand — and the leak was a bug in exactly that hand-written part. This is the single design decision most worth challenging in review.

1.3.4 The allocator, and the page-state tracking beside it

Status, stated first

The live allocator below is unchanged and is what every measured result in this document ran on. The page-state tracking in §1.3.4b is committed and builds clean (354328995), but is shadow only — it changes no allocation decision — and has never been booted. Its assertions have not run once.

The live allocator

The lowest free index is always chosen — still true, still a wear problem

find_first_bit() scans from index 0 and returns the first set bit. With 1 = free that is “give me the lowest-numbered free sector”: strictly ascending while nothing is freed, and after a free it refills the hole from the bottom.

Exposure today is 0.001% of one sector's life per run against a 100,000-cycle rating, so nothing is at risk — but the distribution is wrong in the direction that worsens with uptime. Fixing it is what the tracking below exists to enable.

1.3.4b Page-state tracking — committed, shadow only, unbooted

The target design is a four-state machine — FREE / VALID / DIRTY / ERASING — whose real prize is not wear levelling but moving the erase off the write path. Today ft_ltram_write_page() erases synchronously before every program:

costshare
subsector erase16.4 ms93%
programming a sector~1.2 ms7%

With pages arriving pre-erased from a Free pool, a promotion costs the DMA alone — ~14× faster, and the migration spike measured at 27.6× DRAM (§2.7 T6) should largely stop existing. Background erase removes the erase from the latency path, not from the throughput budget: sustained promotion is still capped near 61 pages/s. Ours is a burst workload, so we get the win.

How each state is represented, and why they differ

staterepresentationsizewhy
VALIDbitmap8 KiBNo ordering needed. bitmap_weight() derives the count from the data, so a count cannot drift away from the thing it describes — the exact bug class that lost 16,502 pages. Disjointness is one bitwise AND
DIRTYbitmap8 KiB
ERASINGone u32 index4 BThe hardware erases one sector at a time, serialised under the backend mutex. A queue would be a container that never holds more than one thing
FREEbucket lists, and nothing else1 MiB + 1.6 KiBDeliberately no free bitmap: free is ~(VALID | DIRTY) minus whatever is erasing, so it is derived at check time and cannot drift. A stored one would be a fourth structure that can be wrong in the same way as what it checks
erase countsu32 ec[65536]256 KiBMust persist while a page is VALID or DIRTY, so the bucket index cannot store it

RETIRED is deliberately absent. It only means something once the parking policy exists — park a permanently read-only page in a nearly-worn sector so it is never erased again — which is a later experiment. Carrying it now would mean a bitmap that is always empty and a line in the report for a feature that does not exist.

Why buckets at 1000-erase granularity with FIFO inside

Not a compromise. While every page shares an erase count they all sit in bucket 0, and pop-head / return-to-tail is round-robin — which is precisely the wear spreading the flat allocator lacks. Exact per-erase-count buckets behave identically at that point and cost 100,000 list heads instead of 101.

The two transitions 1a performs

1c inserts DIRTY and the background erase between the two halves of lt_give_back(). In 1a only FREE and VALID are ever occupied, because a freed page still goes straight back to FREE exactly as it does now.

The erase count is an upper bound in 1a

It is incremented at allocation, because in the current design every allocated page is erased before it is programmed — so allocation and erase are one-to-one, except when a migration fails after allocating, which over-counts by one. Wrong in the conservative direction, and replaced by an erase-completion hook in 1c.

Counts start at 0, which is not the device's history: this chip took heavy unknown wear during FPGA bring-up. Read them as “erases since counting began.”

The five assertions — /sys/kernel/debug/ltram/pagestate

checkcatches
VALID & DIRTY == 0a page in two states
valid + dirty + free_count + erasing == 65536a page lost from every state

The middle three are the redundancy that matters: three independent descriptions of the free set — derived, counted, and walked — that must all agree. That is what turns a silent page loss into failed arithmetic. The file also reports the erase-count min / max / mean / spread and a histogram, which is what will answer “how skewed is the wear?” the first time it runs.

Reading it holds the allocator lock with interrupts off for ~65,536 iterations — a few hundred microseconds. Fine for a file a human reads, deliberately not something a hot path could call. lt_check_fast() is the O(n/64) bitwise subset for that.

What the spinlock is for — and one thing to correct

There are not 48 instances of Linux

One kernel image runs across all 48 cores. This is SMP, not 48 machines agreeing with each other. The cores share one physical address space, one kernel page table, and one copy of every kernel data structure — a single ltram_free_bitmap and a single ltram_alloc_lock at one address, which all 48 cores load and store directly.

So the arbitration problem is real, but it is not consensus between instances. It is 48 execution contexts inside one OS mutating one shared object; hardware cache coherence makes their views agree, and the lock decides who may mutate it now.

A spinlock is one word in memory. spin_lock() atomically test-and-sets it; if another core holds it, this core spins in a tight re-test loop until it is released. It never sleeps — right when the critical section is very short, because putting a thread to sleep and waking it costs far more than the wait.

held forusewhere in this project
nanoseconds — a bit scan and a bit clearspinlock, spin and retryltram_alloc_lock
~16 ms — an erase plus a DMAmutex, sleep and be wokenltram_wp_lock in the backend

Spinning for 16 ms would burn a core for 32 million cycles. Sleeping for ~50 ns of bitmap work would cost more than the work. Same problem, opposite answers, decided by expected hold time.

irqsave prevents a one-core self-deadlock

Not hypothetical: the free path is reachable from softirq, because free_pages_prepare() sits on the batch path taken by reclaim and munmap. That is why the lock was converted in e6f915089. Note it only masks interrupts on the local core; the other 47 are still handled by the lock.

Two details in that code worth noticing

  • __clear_bit / __set_bit, not the atomic forms. The __ variants are non-atomic, which is correct: the spinlock already provides mutual exclusion, so an atomic RMW on top would be redundant cost.
  • The free path tests before setting. A page freed twice — through both the __folio_put_small() hook and the free_pages_prepare() backstop — will not double-decrement. The two guard sites are allowed to overlap safely.

1.4 The write path, and where it attaches to migration

Terminology — “hook” is loose, and worth being precise about

“Migration hook” is not a standard kernel term, and there is no migration_hook API. “Hook” is informal shorthand for a call-out point inserted into a generic path. The kernel does use it formally in a few places — LSM hooks, netfilter hooks — but migration is not one of them.

The precise description of what we added is: a conditional branch inside migrate_folio_extra(), the generic copy routine. Not a registered callback, not a vtable entry — a patch to a core function.

The real extension point, and why it could not be used

The kernel does have a formal migration override: struct address_space_operations::migrate_folio (include/linux/fs.h:433). Filesystems supply one to control how their pages move. It is structurally unusable here, for two independent reasons:

  1. It dispatches on the source, we need to act on the destination. a_ops is reached through folio_mapping(src) — it answers “where did this page come from?” Our entire condition is folio_is_ltram(dst): where is it going? No per-source callback can express that, because the same source folio may be migrated to DRAM or to flash depending only on who allocated the destination.
  2. Clean anonymous folios have no mapping at all. folio_mapping() returns NULL for them, so they take the first branch and never consult a_ops. Anonymous memory is precisely what this policy migrates — see the anon-only filter in §1.6 — so the formal extension point is not on the path we care about.

So the conditional in migrate_folio_extra() is not laziness in place of a proper interface; there is no existing interface with the right shape. If this were being upstreamed, inventing one — a destination-keyed migration operation — would be the main design conversation.

Where exactly it attaches, and why there

mm/ltram.c knows nothing about the FPGA. It calls out through one function pointer, struct ltram_flash_ops::write_page. Until a backend registers, ltram_write_page() returns -ENODEV — that is the safety property, not a gap.

Check this against your criteria: for an LtRAM destination there is no folio_migrate_copy(). The CPU never memcpy's into the flash window — which matters because such stores would be silently discarded by the hardware while still occupying CPU cache lines.

What mode != MIGRATE_SYNC_NO_COPY is guarding against

modemeaningwho uses it
MIGRATE_ASYNCnever block. Bail out of anything that would sleepcompaction's async pass, GUP
MIGRATE_SYNC_LIGHTmay block, but not on writebackcompaction's sync-light pass
MIGRATE_SYNCmay block on anything, including waiting for writeback to finishour scanner, memory hotplug, move_pages()
MIGRATE_SYNC_NO_COPYsynchronous, but the caller moves the data itself — the core must not copydevice migration, where a device DMA engine does the copy

So the condition reads: “unless the caller has said it is handling the data movement itself, program the flash here.” It is a guard against double-programming a sector — writing it once from our path and again from the caller's.

In practice our scanner always passes MIGRATE_SYNC (migrate_pages(&ctx.candidates, ltram_get_new_folio, ltram_put_new_folio, 0, MIGRATE_SYNC, MR_NUMA_MISPLACED, &moved)), so the branch is always taken today. The check exists so that a future caller using NO_COPY does not silently erase and reprogram a sector that already holds the right data — which would cost two extra erases and a window in which the page is neither the old nor the new content.

Note the symmetry two lines further down: folio_migrate_flags() is used for both MIGRATE_SYNC_NO_COPY and LtRAM destinations, because in both cases the data was moved by something other than folio_migrate_copy().

Does ltram_copy_to_flash() drive the FPGA's DMA engine?

Short answer: no — and that separation is deliberate

ltram_copy_to_flash() lives in mm/ltram.c and contains no device knowledge whatsoever. It iterates the folio's pages, kmap_local_folio()s each source page, and calls ltram_write_page(dst_pfn, src), which calls out through the registered ltram_flash_ops::write_page pointer. It cannot touch MMIO; it does not know an FPGA exists.

The device work happens one layer down, in the backend module: ft_ltram_write_page() → trigger_erase() and write_sector().

The descriptor itself

  • One 64-bit store is the entire command. Bits [63:40] carry the length (4096); bits [39:0] carry the source physical address from dma_alloc_coherent()
  • The destination is encoded in the address of the store, not in the payload: io_win + sector*4096. The window is 256 MB precisely so every sector has its own descriptor address
  • The FPGA then reads the source page out of DRAM itself. That is why the dc cvac is mandatory — the data must be visible at the point of coherency before the descriptor is posted, and the wmb() orders those two
  • Completion is polled from a free-running byte counter in the status word, read back through the same window

On “AXI-Lite” specifically — I cannot confirm this from the driver

From the CPU's side this is a writeq into an ioremap()d (uncached, Device-nGnRE) window whose transactions cross ECI. What that lands on inside the FPGA — an AXI-Lite slave, or something else — is not visible in the driver source, and I would be guessing.

Two observations that argue against a plain AXI-Lite register bank: the window is 256 MB, and the address carries the destination sector. That is a memory-mapped command region, not a small register file. The FPGA-side answer is in the shell RTL (nor_read_subsystem.v, the write_manager), not here.

1.5 The invariant, and the four places that enforce it

The invariant

A flash-backed page is never writable, and never reaches the buddy allocator. A store to the NOR read window is silently discarded by the hardware — no fault, no error — so a writable flash PTE loses data with no diagnostic whatsoever.

Why the fourth site exists, and why it is the important one

release_pages() and free_unref_page_list() — the batch path that process exit and munmap take — bypass __folio_put_small() entirely. With only sites 1–3, flash pages hit the backstop, were correctly kept out of buddy, and were then dropped: 16,502 leaked in one evening. Hooking the funnel covers every caller by construction instead of by enumeration.

1.7 The promotion predicate, verbatim

And the re-arm, which is what makes written mean anything on the next pass:

Why pte_write() and not pte_dirty()

On arm64 pte_dirty() is pte_sw_dirty || pte_hw_dirty, and pte_sw_dirty is bit 55, a one-way latch: set on first write, set again by pte_wrprotect(), preserved by pte_modify() across mprotect, and cleared only by pte_mkclean() — which is called nowhere in this subsystem. This CPU has no hardware DBM (ID_AA64MMFR1_EL1 HAFDBS = 0) and arm64 has no soft-dirty at all. Measured consequence of asking the wrong question: 13,247,550 of 13,258,954 scans rejected, zero target pages promoted, ever.

pte_write() has an answer that can change, and one the scanner itself changes.

2 · Method

2.1 The measurement boundary — what is inside the timer

Inside the timer

  • The ITERS × N × N matrix–vector inner loop, and nothing else
  • Every read of W, which is what crosses to NOR once promoted

Outside the timer

  • memset(y) — the accumulator reset
  • cache_scrub() — the LLC eviction
  • SHA-256 digest computation and comparison
  • All printf, including the POINT line
  • The entire --phys pagemap census and move diff

now() is clock_gettime(CLOCK_MONOTONIC). The clock stops before the digest, so verification never inflates a timing.

2.2 The cache scrub, exactly

  • Capacity eviction, not dc civac. One read per 128 B line over a buffer 4× the LLC steamrolls every set, needs no privilege, and does not depend on which cache-maintenance instructions EL0 may issue
  • Sized 64 MiB against a 16 MiB LLC. This machine has no private L2: 16 MiB is the LLC and it is shared by all 48 cores
  • The volatile sink is what stops the compiler deleting the loop
  • The store pass exists so the scrub buffer cannot itself be promoted. It keeps pte_write() true, so the policy rejects and re-arms it every pass. Without it the buffer is anonymous and read-mostly — a perfect candidate — and mmap puts it below the weights, so the scanner reaches it first

Measured: the scrub changes nothing at this size

DRAM baseline warm 0.107 s, cold 0.107 s — identical to four decimal places over six runs each. A 64 MiB linear sweep against a 16 MiB shared cache already self-evicts before it wraps, so these timings were always effectively cold. The flush is kept because it forecloses the objection, not because it changed an answer. If you need a warm-cache number, this method will not give you one.

2.3 What one measured point is

  • --iters 1 --runs N → one point = one complete pass over the whole weight matrix, from a scrubbed cache. No pass shares a cache with itself
  • --iters K with K>1 makes a point K passes, and iterations 2..K are warm. The station-4 runs used K=60; the station-7 measurement used K=1
  • Each point emits POINT <run> <seconds> <wall_offset>

2.4 How residency is measured — independently of the kernel's own counters

  • ltram-inspect <pid> <name> <start> <len> reads /proc/<pid>/pagemap directly
  • PM_PRESENT = bit 63; PFN = bits 0..54
  • Each PFN is compared against /sys/kernel/debug/ltram/{start_pfn,end_pfn} and classified LtRAM / DRAM / not present
  • This is page-table truth, not the policy's opinion — it would catch a counter that lies
  • Must run as root. Unprivileged pagemap on this box reports every page absent; verified, and the tool warns rather than reporting a silent zero
  • The result buffer is checked too: any page of it on flash is a failure, not a low percentage, because it is written every iteration

2.5 How the two time bases are aligned

  • matmul prints TSTART <epoch> from CLOCK_REALTIME at the run loop's origin, after the fill
  • The residency sampler logs absolute epoch times; offset = epoch − TSTART
  • This removes all guesswork about how long the fill took. An earlier version inferred it, which is exactly the kind of assumption that produces a plausible wrong graph

The rule

A faster run with a different digest is corruption, not a result. On this hardware corruption is silent by default, so the digest gate is not a formality — it is what caught the stale-cache-line bug, at run 12 of 15.

--protect-weights is an experiment control, not a kernel hint. The policy reads PTE state and never looks at VMA flags. It was proven irrelevant: a run without it reaches the same promotion rate.

2.7 Every test run, with method and result

T1 — detection, with and without an application hint

  • Method: two phases, same binary, same size, same 240 s attach window, counters sampled before/after and reported as deltas so no reboot is needed between them. Phase A passes --protect-weights; phase B passes nothing. Backend deliberately not loaded, isolating detection from the write path
  • Result: phase B rej_writable == rearmed == 50,179 against exactly 50,176 weight pages. Same sel_isolated as phase A (7,488 vs 7,456) → the hint bought nothing
  • Limit: promoted 0 by construction; proves nothing about flash

T2 — end to end, first attempt

  • Method: 64 MiB weights, --iters 60 --runs 15, promote_batch=256, backend loaded
  • Result: 16,384/16,384 resident, digest held 15/15, steady state 31.299 s vs 6.432 s control
  • Caveat you must apply: this run passed for the wrong reason. A page leak meant no sector was ever reused, so the stale-cache-line bug underneath could not fire. Do not cite its 15/15 as evidence the write path is sound

T3 — end to end after the leak and anon fixes — FAILED

  • Method: identical, promote_batch=32
  • Result: digest changed between run 11 and run 12, exit 44. run1 8873ba56… vs run12 8d57ab9c…
  • Cause: rd_win is ioremap_cached and an FPGA-side erase/program does not invalidate CPU caches. inval_sector() existed in the backend for exactly this and the migration path never called it

T4 — end to end after the cache-invalidate fix — PASS

  • Result: digest identical 15/15, promoted 6,784 == writes_ok 6,784, promote_failed 0, writes_failed 0, pages_in_use 1 after exit
  • Does not reach steady state: at batch=32 only ~21% had migrated by run 15, so its 13.766 s mean is a ramp, not a plateau, and is not comparable to T2's 31.299 s

T5 — writeback: the fault path back to DRAM — PASS

  • Method: fill 32 MiB with pattern A; stop writing; let the policy promote it by reading only; at ≥90% residency write pattern B over every page; verify. The pattern is position-dependent (idx * 0x9E3779B97F4A7C15 ^ epoch) so a page restored from the wrong sector fails too. The scanner is detached 2 s before the write so a real failure cannot be confused with a page re-promoted under the writer
  • Result: 7,517/8,192 (91.8%) resident; STALE 0, WRONG 0; demoted +7,519 against 7,517 resident — one demotion per flash-resident page
  • Bonus: rej_writable == rearmed == 8,211 on a program that is not matmul → transparent detection confirmed independently. And late_free moved by only 7, showing the single-page and batch free paths are distinct routes, both covered

T6 — the cost measurement

  • Method: --iters 1 --runs 1500 --flush 64, twice: once with no backend and no policy (control), once with the policy attached. Residency sampled every 3 s and aligned by TSTART
  • Result: control 0.1075 s (sd 0.09%, n=1500); peak 2.971 s; plateau 0.5139 s (sd 0.08%, n=222) = 4.78×. Digest b1b51e52… identical across both runs
  • Known contamination: in this run the 64 MiB scrub buffer was itself promoted first, consuming the first 457 s. Effect on the timed passes was +1.5% (0.109 vs 0.1075) because the timed region never touches that buffer. Fixed by the store pass in §2.2; the clean re-run completed but its data has not yet been retrieved

4 · What would make me distrust these numbers

Stated so you can check them rather than take my word

  • The 4.87× from T2 came from the run whose sectors were never reused, i.e. before the cache-invalidate fix. It agrees with T6's 4.78×, which is reassuring, but it is not an independent confirmation from a correct kernel. A steady-state re-measure on the current kernel has not been done
  • The on/off delta mixes three things: flash read latency, NUMA distance, and migration cost. Separating them needs a DRAM-backed node-1 control — same migration, same distance, no flash — which does not exist. I will not attribute the delta to flash latency until it does
  • One access pattern. A 64 MiB sequential sweep. Random access, or a working set that fits in LLC, would land somewhere else entirely. 4.78× is not a constant
  • Above the 256 MB window is completely untested. Every result here depends on each page getting its own sector, written exactly once. Above the window that stops being true and phase 3 stops being a plateau
  • A write racing an in-flight promotion is untested — T5 deliberately avoids that race rather than exercising it
  • folio_isolate_lru() refuses 3–20% of selections across runs and I cannot explain the variance
  • Step 5's negative test has never run. fail_writes=1, then assert the migration fails with the page still in DRAM and correct. Without it, hook placement is argued from code reading, not demonstrated — the positive path passes whether or not the hook precedes folio_migrate_mapping()
