Status, Corrected

Six lines on the status slide say something the code does not do. Then what is actually left on the scanner, which is one decided change blocked behind one undecided policy. And one thing we still cannot explain.

Six corrections

Each pairs the line as written against what the tree does today.

as writtenErase count metadata: saved before and after each test run and before power off.
not implemented

The kernel half landed: /sys/kernel/debug/ltram/erase_counts reads and restores the array, and restoring rebuilds the allocator's buckets. The userspace unit that reads it at shutdown and writes it back at boot does not exist, so counts still reset every boot.

Two things to say alongside it. Unclean shutdown will lose whatever accumulated since the last save, so every count is a lower bound. That is the right direction to be wrong in: undercounting sends a write to a sector believed fresher than it is, while overcounting would crowd the sectors still believed fresh, which is the exact failure the mechanism exists to prevent. And the counts mean "erases since counting began", not the device's history. This chip took heavy unknown wear during FPGA bring-up and nothing can recover that.

as written, and now trueErase thread issues erases every 30 ms.
true as of tonight

It was not true this morning. The worker batched sixteen erases back to back and re-armed with zero delay, which kept the device busy essentially continuously during a drain. Since NOR cannot serve a read while a sector is erasing, that was the worst possible shape for read latency, and the run that recorded erase_deferred 931 was the idle gate trying to prevent something it structurally cannot.

a workload is attached30 msone erase, then a 13.6 ms window for reads
nothing attached0 msnothing to disturb, drain at the device's ~61/s

33 erases a second is not a compromise. Every dirty sector exists because a page was promoted, so the erase rate is pinned to the promotion rate, which is 32/s at the default batch and capped at 41.5/s by the wear budget regardless. The capacity up to 61/s was never needed while something is running.

One word in the original line is still wrong: it polls, it is not woken by an event. Nothing tells the worker that the clean count crossed the watermark, so the interval is purely how stale that answer may be. A TODO in the code records the fix, which is for the allocator to queue the work directly when it drops below the low mark.

as writtenBoot scan reads the array to learn which pages are free versus dirty, to minimise erase latencies.
right mechanism, wrong reason

It is there for correctness, not latency. Page state lives in RAM while the flash keeps its bits, so after a reboot the kernel would believe written sectors are blank. With inline erase off, programming a sector that already holds data yields the bitwise AND of old and new, silently and with no error on any path.

The alternative was to assume everything is dirty, which is safe and costs 65,536 erases and about 18 minutes to blank an array that is usually mostly blank. Reading it costs 256 MB through the window at roughly 124 MB/s, so about two seconds, and reports the truth rather than either assumption.

true, but it is the rare path

as writtenWear history: erase counts reset every boot, no long-term memory.
half fixed

Kernel side done tonight. Userspace side not written. So the statement is still true in practice and the remaining work is a systemd unit and a file, not a design question.

as writtenMedium latency: the 10× per-access figure is from driver annotations, not measured.
now measured, and it depends on the access pattern

Two measurements, and they disagree for a real reason rather than by error.

access patternDRAMNORratio
sequential streaming (matmul)——9.6×
random dependent chase130 ns901 ns6.9×

DRAM is about 1.6× faster under sequential access; NOR is 1.05× faster, which is to say barely. Prefetching and memory-level parallelism recover a lot on DRAM and almost nothing on NOR. So there is no single number for "how much slower is the medium", and the honest phrasing names the pattern.

The chase number is further diluted by page-table walks, which cost the same on both media and therefore drag the ratio down. That is consistent with a line-level ratio near 10 plus a common offset of roughly 48 ns.

The scanner

One change, decided and not built, blocked behind one policy that is not decided.

Built and running

The walk resumes from a cursor rather than restarting, so every region is reached. Selection is one line, !pte_write(), with no per-page metadata. Nine filters reject file-backed, KSM, DMA-pinned and large folios before anything is chosen. The counters partition: ptes_examined = was_written + chosen + lru_refused.

Decided, not built

The pacing. Today it is msleep(1000), unconditional, and that constant absorbed the entire benefit of moving the erase off the promotion path.

promotion rate = batch / (work + sleep)

                work for 32   plus 1 s    rate    measured
inline erase       0.563 s     1.563 s   20.5/s     24.1/s
background erase   0.038 s     1.038 s   30.8/s     28.8/s

delete the sleep:  57/s against 842/s  =  14.8x

A one second constant dwarfs both work times and compresses a 14.8× difference into 1.5×. Making promotion fourteen times cheaper changed nothing observable, because both numbers were already sitting behind it.

The fix is adaptive backoff driven by ctx->nr, which the scanner already has when a pass ends. Batch filled means more work is waiting, so come straight back. Nothing found means back off.

Argued down, with the numbers

Two fixed intervals tied to write and erase timing. The scanner already self-paces, because ltram_write_page() blocks and the thread cannot outrun the device whatever the timer says. Hard-coded device constants are also wrong under contention, wrong if inline_erase flips, and wrong on the next hardware.

Splitting the scan from the migration. In a page-dense region the walk costs about 4 µs to find 32 candidates and the migration costs 38 ms. Scanning is 0.01% of a cycle that is 96% sleep. The split would recover that 0.01% and cost a bounded queue, backpressure, and per-page revalidation against a page that may have been written or unmapped while it waited. It becomes right for multi-process, where it is structural rather than an optimisation.

The blocker

The fixed second is doing two unrelated jobs: pacing, badly, and wear limiting, invisibly. Remove it and you fix the first while silently deleting the second. Unleashed, the scanner promotes at roughly 842 per second against a budget of 41.5.

Today that limit is an accident of promote_batch and scan_interval_ms multiplying to about the right number. Nothing states it and nothing checks it, and we exceeded it ourselves this week running the batch at 512 and 2,048 for measurements.

Settled: a deadline formula, remaining erases over remaining seconds, which self-corrects for periods of light use. A token bucket to separate burst from sustained, so a workload's migration transient runs at device speed while the long-run average stays at budget. Charging at promotion rather than at erase, since they are one to one. The instantaneous cap is free, because the flash write blocks.

Not settled: calendar time or powered-on time; what should happen when the budget is exhausted; and where t=0 lives if the erase-count blob is ever lost.

Once that is decided the backoff is about ten lines. The governor is the part that decides whether the hardware survives five years.

One thing we cannot explain

Small, and unresolved, which is why it is here rather than buried.

matmul's input vector x is never promoted. Every run reports PHYS end input LtRAM 0 (0.0%).

It should be. All three buffers come from the same allocator, mmap(PROT_READ|PROT_WRITE), so x gets its own three-page region rather than sharing heap pages with write-active data. It is written exactly once, at line 570, and only read afterwards, which is precisely the pattern the policy selects for. The weights in the same address space reach 100% residency.

Three pages out of 8,196 changes no result, which is why it has not been chased. It is answerable rather than mysterious: /sys/kernel/debug/ltram/promotions now records the source pfn of everything promoted, so comparing that against the first pfn that --phys prints for the input region says directly whether those three pages were ever candidates.

Worth knowing before someone asks, because the honest answer is that we noticed and have not looked.

What is left, in order

  1. Settle the sustained-rate policy. Everything below waits on it
  2. Then the scanner backoff. Ten lines, with the governor as its ceiling
  3. Then re-measure. One pair of runs gives both the migration throughput ratio and the cost curve during migration
  4. The erase-count userspace unit. A systemd unit and a file, no design left
  5. Leave the thread split alone until multi-process makes it structural
