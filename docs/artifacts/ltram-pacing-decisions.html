Erase and Scan Pacing

Two kernel threads run behind the placement policy: one erases sectors, one finds pages to promote. Neither does anything difficult. Almost all of the design effort went into deciding how often each one wakes up, and one of those decisions quietly cost the project its headline number. This records what was chosen, what was rejected, and what is still open.

Part one: the erase worker

Its job is a four step loop. Pick a sector holding stale data, tell the FPGA to erase it, wait for the erase to finish, mark it free. The waiting is what makes every other decision.

Timer or workqueue

shipped

The constraint

An erase takes about 16.4 ms. At 2 GHz that is 33 million clock cycles. Spinning on a status register for that long would occupy an entire core doing nothing, 61 times a second. The code has to give the CPU up and be woken later.

Why that rules out a timer

Kernel code cannot sleep everywhere. Process context, meaning a real thread with its own stack and scheduler entry, can sleep, because there is something to put to sleep and something to wake. Softirq and interrupt context cannot: that code is borrowing the current CPU and stack from whatever task happened to be running, and there is no thread to suspend. Sleeping there wedges an unrelated task and the kernel deadlocks or panics.

Linux timer_list callbacks run in softirq context. A timer callback therefore cannot call msleep(). It could only notice that work exists and wake a thread to do it, which is a hand written workqueue.

The choice

delayed_work is the built in version: a timer that fires and hands the work to a pool of kernel threads. The callback runs in process context and is allowed to sleep. The decision is not about performance or elegance. The function must sleep for 16 ms and only one of the two options permits it.

Fixed sleep, or ask the device

shipped

Rejected: sleep 16.4 ms and assume

Wrong in both directions, and the second one is dangerous.

If the erase runs long, because the device was busy or the sector needed retries, the sector is marked free while it is still erasing, and the next writer programs into a half erased region.

If the erase never started, because the trigger write was dropped or the FPGA missed it, the code sleeps and then marks an unerased sector blank with complete confidence. Nothing reports a problem. The allocator hands it out as fresh, and NOR programs by clearing bits, so the next write produces the bitwise AND of old and new data. Silently. That surfaces much later as wrong results with nothing to trace back to.

Chosen: poll the device's erase counter

The FPGA maintains a count of completed erases in its status word. Read it before triggering, poll until it increases, give up after a two second ceiling and return the sector to the dirty state.

A fixed sleep cannot distinguish finished from never started, and those two need opposite responses. The interface header states the rule directly: waiting on the counter rather than a fixed sleep is the difference between noticing a dropped trigger and corrupting the next program.

Three status bits, not two

shipped

The original specification was HW_BUSY == 0 && SCH == 0. The implementation adds a third term.

return !ST_HW_BUSY(w) && !ST_ER_INFL(w) && ST_SCH(w) == 0;
bitmeaningwhy it is needed
HW_BUSY (56)NOR controller mid operationthe obvious one
ER_INFL (57)an erase triggered but not retireda longer window than the other two. Without it the worker can trigger a second erase while one is outstanding, and the device does one at a time
SCH (58 to 60)read subsystem state machinethe only visibility into read traffic that exists. Reads never reach the driver, they are plain loads through a cacheable window, so this register is the only way the kernel can see them at all

The device must look idle three times in a row, one millisecond apart, before a 16.4 ms erase is committed. A single sample can land in the gap between two reads and report quiet while a workload is mid stream.

Re-arming: zero delay while draining

shipped

A workqueue item runs once. Nothing calls it again unless it schedules itself, and the delay it picks is the worker's pace. The plan called for 15 ms then 1 ms. What shipped is different.

queue_delayed_work(system_unbound_wq, &lt_erase_work,
                   backlog ? 0 : msecs_to_jiffies(erase_poll_ms));

The zero is arithmetic. The device sustains about 61 erases per second. A worker that erased a batch and then waited even 50 ms would run 20 times a second, and no amount of batching inside one invocation changes the fact that it is asleep for most of the wall clock. Coming straight back while sectors remain makes the device the limit rather than the scheduler.

The 50 ms applies only when the queue is empty, where the worker is checking whether work appeared and doing that 61 times a second would be pure waste.

Part two: the scanner

This is where the project lost its headline number. The next card is the most consequential thing in this document.

The 1 s interval absorbed the 14×

decided, not built

What the loop does

while (!kthread_should_stop()) {
        ltram_scan_once();
        msleep_interruptible(scan_interval_ms);   /* 1000 */
}

ltram_scan_once() includes the migration, and migration blocks on the device. So the sleep is a gap, not a period, and the promotion rate is batch / (work + sleep).

work, 32 pagesplus 1 spredictedmeasured
inline erase0.563 s1.563 s20.5/s24.1/s
background erase0.038 s1.038 s30.8/s28.8/s

Now delete the sleep and recompute: 57/s against 842/s, a ratio of 14.8.

The finding

The 14× was always real. A fixed one second sleep dwarfs both work times and compresses a 14.8× difference into 1.5×. Moving the erase off the critical path made promotion 14 times cheaper, and the sleep it was already sitting behind absorbed the entire gain.

Worth stating plainly, because it changes how the result should be reported: the design decision was right and the published justification was wrong. Not "promotion is 14× faster" as an end to end claim, but "the promotion path costs 14× less device time, which the scanner's pacing currently throws away."

Adaptive backoff, not two fixed intervals

decided, not built

The proposal

Wake 1.5 ms after a pass when the erase engine is off, since that is roughly what a write costs, and 18 ms when it is on, to cover an erase.

Why not

The scanner is already self pacing, because ltram_write_page() blocks. The thread physically cannot promote faster than the device permits, whatever the timer says. It does not need to be told how long a write takes. It finds out by waiting for one.

Hard coded device constants also age badly. 1.5 ms and 18 ms are true for this bitstream, this chip, and an idle bus. They are wrong under contention, wrong if inline_erase flips, wrong when a sector needs a retry, and wrong on the next hardware. Two magic numbers that silently stop matching reality.

Chosen instead

Drive the delay from productivity, which the scanner already knows, because ctx->nr is sitting there when the pass ends.

at end of passmeansdelay
nr == promote_batchmore work than one pass could takezero
0 < nr < batchfound some, ran out of PTE budgetshort
nr == 0nothing eligible in this regionback off toward ~1 s

No timing measurement, no device constants, one integer that already exists.

Why fast scanning must be conditional

hazard

The third row above matters more than the others, and a short fixed interval would make it worse.

Measured on hardware, over ten seconds of a saturated run:

ptes_examined     delta 32799
was_written       delta 32799     <- every one was writable
chosen            delta 0         <- none promoted

Every PTE examined was rejected. Those were scrub buffer pages, dirtied on every workload pass. Each rejection costs a ptep_set_wrprotect plus a flush_tlb_page, and a TLB flush here is an inter processor interrupt. Roughly 3,300 IPIs per second aimed at the cores running the workload.

At a 1.5 ms interval that becomes tens of thousands per second, and none of it appears in the scanner's own accounting. It shows up as the workload mysteriously getting slower. A scanner that wakes every 1.5 ms over write active memory is a denial of service against the thing it exists to help.

Splitting scan from migrate

rejected for now

The proposal

Scanning is CPU work, migration is waiting on a device. Decouple them with a queue so the scanner keeps finding candidates while the migrator drains, and accept that the migrator must re-check whether a queued page changed while it waited.

The ratio that settles it

Walking one PTE costs on the order of 100 ns. Promoting one page costs 1.2 ms with background erase. The scanner stops as soon as it has promote_batch candidates, so in a page dense region, which is the case that matters during migration:

walk to find 32 candidates      ~4 us     (32 to 100 PTEs)
migrate 32 pages                ~38 ms    (device bound)
sleep                          1000 ms

Scanning is 0.01% of the cycle. The sleep is 96% of it. Decoupling recovers the 0.01% and leaves the 96% untouched.

What it would cost

  • A bounded queue, and backpressure when the device falls behind
  • A second thread
  • Re-validation per page, and it is worse than it first looks. Between queueing and migrating, a page can be written, unmapped, or its process can exit. The isolated folio holds a reference so it will not be freed, but the mapping can vanish, so the migrator has to re-take the page table lock and re-check pte_write() for every entry

When it becomes right

Not throughput. Multi-process. Once several processes are candidates, one scanner per address space feeding a single migrator is the natural structure, because the device is serial. Then the queue is not an optimisation, it is the shape of the problem. Build it when multi-process support arrives, not before.

The open question

Burst rate against the wear budget

open

Zero delay does exactly the right thing for a migration transient and exactly the wrong thing forever.

promote_batch = 32 at one pass per second was never chosen for throughput. It is the wear budget: 65,536 sectors times 100,000 erases, spread across five years, comes to 41.5 erases per second sustained. The current settings sit just under that by construction.

Remove the sleep and the loop promotes at whatever the device allows, roughly 842 per second. That is twenty times the budget. Sustained, it retires the chip in about three months instead of five years.

Two limits, currently conflated

  • Burst rate should be as fast as the device allows, so a workload's migration transient is short
  • Sustained rate must stay near 41.5 per second, or the wear model is fiction

Proposed mechanism

A token bucket. Refill at the sustained rate, allow a depth of a few thousand promotions, and let the productivity signal drive the delay only while tokens remain. A workload that migrates 8,000 pages once and then settles spends its bucket in ten seconds and refills over the following three minutes. A workload that would churn continuously gets throttled to the budget automatically.

This also makes the wear guarantee explicit rather than emergent. Today it is a property of two tunables that happen to multiply to the right number, which nothing enforces and nothing checks. Anyone raising promote_batch for an experiment, as we did at 512 and 2048 this week, silently blows through it. With a bucket the limit is stated once, in one place, and an experiment that exceeds it has to say so.

Settle this before writing the backoff. The backoff is easy. The governor is the part that protects the hardware.

Related decisions from the same session

Erase counts across reboots

shipped

The counts survive nothing on their own. The array is allocated zeroed at every boot while the flash keeps its wear, and the boot scan cannot help: it recovers which sectors are blank by reading them, but no sector records how many times it has been erased.

Within one boot the levelling works, which is where the improvement from 1,518 allocations on a single sector down to a peak of 1 comes from. Across boots every sector looks equally fresh and it starts over.

/sys/kernel/debug/ltram/erase_counts is a header plus one u32 per page, 256 KB for a 256 MiB window. A userspace unit reads it before shutdown and writes it back after boot.

The failure direction was chosen deliberately

Unclean shutdown loses whatever accumulated since the last save, so every count is a lower bound. That is the right way to be wrong. Undercounting sends a write to a sector believed fresher than it is and costs some wear. Overcounting would make the allocator avoid good sectors and crowd the ones it still believes are fresh, which is precisely the failure this mechanism exists to prevent.

The counts mean "erases since counting began", not the device's history. This chip took heavy unknown wear during FPGA bring up and nothing can recover that.

How to measure the 14×

designed

It will not appear in workload latency, because promotion is asynchronous. It appears in migration throughput, which is what the claim was always about.

per promotiondevice limited8,190 pages
inline erase17.6 ms57/s~144 s
background erase1.2 ms833/s~10 s

The metric is time to 100% residency, read from the sampling the harness already writes every five seconds. Same workload, same page count, only inline_erase changes. Raise promote_batch so the batch limit stops being the ceiling and the device becomes it.

Expect nearer 9× than 14× in practice, because the fast side hits the scanner's own limits before it reaches 833/s. The honest claim is that migration completes roughly an order of magnitude faster, with 14× as the per promotion device cost.

The other number this produces

The same pair of runs gives the migration cost curve, previously called station 7, which is a name that means nothing to anyone. It measures the workload's per pass cost while migration is happening, as opposed to after it settles. Its earlier result peaked at 2.971 s against a 0.1075 s baseline, so 27.6× at the worst moment, falling back toward 4.9× once migration finished. That peak is the price of moving data, paid once, and it was measured with inline erase.

What to do next, in order

  1. Settle the sustained rate policy. The token bucket, or an argument for something else. Everything below depends on it
  2. Then the adaptive backoff. Three lines of state in the scan thread, using ctx->nr, with the governor as its ceiling
  3. Then re-measure. One pair of runs gives both the migration throughput ratio and the migration cost curve
  4. Leave the thread split alone until multi-process support makes it structural rather than an optimisation
